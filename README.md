# Agentic Development Practices

> A methodology for structured AI-assisted development that prevents technical debt while maximizing productivity.

## The Problem: Vibe Coding

In February 2025, Andrej Karpathy (OpenAI co-founder, former Tesla AI lead) coined the term **"vibe coding"** - an approach where developers provide natural language descriptions and let AI generate code without rigorous oversight.

It sounds efficient. It's actually a trap.

### The "Please Claude, Build Me a Website" Failure Mode

```
Developer: "Please build me an e-commerce site to sell shoes"
AI: *generates 2,000 lines of working code*
Developer: "Ship it!"

Week 1: It works!
Week 4: "Why is checkout broken?"
Week 8: "Nobody understands this codebase"
Week 12: Complete rewrite required
```

This isn't hypothetical. Research confirms it's happening at scale.

## The Research Is Clear

### Academic Studies

#### Stanford University: The False Confidence Problem

In a landmark study published at **ACM CCS 2023**, Stanford researchers (Perry, Srivastava, Kumar, and Dan Boneh) conducted the first large-scale user study on AI-assisted code security:

> "Participants who had access to an AI assistant wrote **significantly less secure code** than those without access. [...] Participants with AI access were **more likely to believe they wrote secure code** than those without access."
>
> — [Do Users Write More Insecure Code with AI Assistants?](https://dl.acm.org/doi/abs/10.1145/3576915.3623157) (ACM CCS 2023)

This is the core danger: **AI makes developers both worse AND more confident**.

#### Carnegie Mellon: No Quality Improvement Over Time

CMU researchers tracked 807 GitHub repositories using Cursor AI from January 2024 through August 2025:

> "AI briefly accelerates code generation, but the underlying code quality trends continue to move in the wrong direction. [...] No reversal in code quality issues despite improvements in models and tooling."
>
> — [Speed at the Cost of Quality: How Cursor AI Increases Technical Debt](https://arxiv.org/pdf/2511.04427) (arXiv 2025)

Even as models improved (Claude 3.5 → 3.7, agent mode), the debt kept accumulating.

#### IEEE Systematic Literature Review

A comprehensive review of 3,104 peer-reviewed studies on LLM-generated code security found:

> "12–65% of generated code snippets are non-compliant with basic secure coding standards or explicitly trigger CWE-classified vulnerabilities."
>
> — [State of the Art of the Security of Code Generated by LLMs](https://ieeexplore.ieee.org/document/10795572/) (IEEE 2024)

### The "Spaghetti Point"

Around **month 3**, vibe-coded projects hit a wall of complexity where adding new features breaks existing ones and velocity drops to near zero. This is the point where the accumulated technical debt becomes unmanageable.

### The Workforce Paradox

[Forrester predicts](https://www.salesforceben.com/2026-predictions-its-the-year-of-technical-debt-thanks-to-vibe-coding/) that 75% of technology decision-makers will face severe technical debt by 2026. Meanwhile, 54% of engineering leaders plan to hire fewer juniors due to AI—yet AI-generated technical debt requires *human judgment* to fix, precisely the judgment juniors develop through years of experience.

## The Solution: Disciplined Agentic Development

This repository contains battle-tested patterns for **controlled** AI-assisted development:

```
.
├── agents/           # Role-specific AI personas with bounded responsibilities
├── rules/            # Architectural constraints injected into every session
├── skills/           # Reusable capabilities agents can invoke
└── commands/         # Standardized operations
```

### Core Principles

1. **Constrained Agents**: AI operates within defined boundaries, not freeform
2. **Architectural Rules**: Style, patterns, and structure enforced automatically
3. **Separation of Concerns**: Different agents for different responsibilities
4. **Human Oversight**: AI proposes, human disposes
5. **Reusable Patterns**: Consistency across projects and teams

### Security Rules (`rules/shared/security.md`)

Addresses the research finding that **25-30% of AI-generated code contains CWEs**:
- Injection prevention (SQL, command, code)
- Secrets management (no hardcoded credentials)
- Input validation at boundaries
- Auth/authz patterns (IDOR prevention)
- Cryptography best practices
- Dependency security
- Platform-specific rules (Flutter secure storage, certificate pinning)

## Why This Works

### Vibe Coding Approach
```
Input: "Build me a FastAPI backend"
Output: 500 lines of coupled, untested code
Result: Works today, unmaintainable tomorrow
```

### Disciplined Agentic Approach
```
Input: "Build me a FastAPI backend"
+ Agent: python-fastapi (knows layered architecture)
+ Rules: SOLID, testing requirements, module limits
+ Constraints: No business logic in routers, typed everything

Output: Properly layered, tested, maintainable code
Result: Works today, scales tomorrow
```

## The Process: Command Chain Governance

The anti-pattern:
```
Developer: "Just fix it!"
AI: *makes 47 changes across 12 files*
Developer: "Ship it!"
Result: Chaos, untraceable changes, new bugs
```

The disciplined approach uses a **command chain** with mandatory checkpoints:

### Two Workflows

| Workflow | Purpose | Commands |
|----------|---------|----------|
| **Development** | Build features from issues | `/plan-release` → `/plan-validate` → `/implement-phase` → `/check` → `/fix-check` |
| **Release Gate** | Audit & fix before release | `/review-architecture` → `/plan-fix` → `/plan-fix-validate` → (per phase: `/implement-fix-phase N` → `/check` → PR → merge) → `/validate-review` → `/heal-review` |

### Symmetry — both workflows have the same shape

The release-gate flow is deliberately a mirror of the development flow. Reviewers and AI Devs see the same loop whether they're shipping a feature or paying down architectural debt:

| Stage | New feature | Refactoring |
|-------|-------------|-------------|
| **1. Discovery** | Issue / spec / PRD | `/review-architecture` → `REVIEW.md` |
| **2. Plan** | `/plan-release` → `IMPLEMENTATION_PLAN.md` (+ `IMPLEMENTATION_PLAN_PHASE_N.md` when ≥2 phases) | `/plan-fix` → `FIX_PLAN.md` (+ `FIX_PLAN_PHASE_N.md` when ≥30 fix units or ≥3 themes) |
| **3. Validate plan** | `/plan-validate` — catches Sonnet-readability gaps before any subagent runs | `/plan-fix-validate` — same Sonnet-readability check **plus** a unique-to-fix step that re-runs every violation grep pattern right now to catch stale findings (REVIEW drift, already-fixed work) before any subagent dispatches |
| **4. Per-phase implementation** | `/implement-phase N` — creates `phase-N-<slug>` branch, dispatches subagent | `/implement-fix-phase N` — creates `fix-phase-N-<theme>` branch, dispatches subagent |
| **5. Per-branch quality gate** | `/check` | `/check` *(same command — branch-agnostic)* |
| **6. Self-correct on the branch** | `/fix-check` | `/fix-check` *(same harness — works on any branch)* |
| **7. Ship the phase** | `gh pr create` → CI → reviewer → merge | `gh pr create` → CI → reviewer → merge |
| **8. Per-phase verification (post-merge)** | *(covered by `/check` + CI)* | `/validate-review N` — re-runs the phase's grep patterns whole-codebase |
| **9. Final verification (after all phases)** | *(implicit — feature is "done" when its phases ship)* | `/validate-review` — every original `REVIEW.md` finding must be resolved |
| **10. Self-correct audit gaps** | *(n/a)* | `/heal-review` — only if `/validate-review` finds gaps |
| **11. Status tracking** | `IMPLEMENTATION_STATUS.md` | `FIX_STATUS.md` |

The middle of the table (stages 4–7) is **identical** — same branch-create → dispatch → check → fix-check → PR → merge loop, just different prefixes (`phase-` vs `fix-phase-`). The asymmetry at the top (refactoring has an explicit audit step) and the bottom (refactoring has explicit completeness verification) reflects refactoring's stronger "did this really do what I claimed?" obligation.

### Development Workflow

```
/plan-release GH#301, GH#404     # Design & split into phases
        │
        ▼
    IMPLEMENTATION_PLAN.md + per-phase specs (detailed, Sonnet-ready)
        │
        ├─ User reviews / edits plan
        │
        ▼
/plan-validate                    # Verify specs are complete
        │
        ├─ ✅ READY → proceed
        ├─ ⚠️ NEEDS REFINEMENT → fix plan → re-validate
        │
        ▼
/implement-phase 1 (creates phase-1-* branch) → /check ──┬─→ gh pr create → CI → merge
/implement-phase 2 (creates phase-2-* branch) → /check   │
/implement-phase 3 (creates phase-3-* branch) → /check   │
                                                          │
                                                  violations found?
                                                          │
                                                          ▼
                                          /fix-check → re-run /check → gh pr create → merge

(Solo prototypes can stay on main; /check then proposes a direct
commit instead of a PR. See your project's USERGUIDE for the
formal-vs-fast trade.)
```

### Release Gate Workflow

```
/review-architecture             # Full codebase audit (5 parallel agents)
        │
        ▼
    REVIEW.md (findings + migration plan)
        │
        ▼
/plan-fix                        # Expand findings → concrete HOW TO FIX
        │
        ├─ Small audit (<30 fix units, 1–2 themes)
        │   → FIX_PLAN.md (single-phase)
        │     /fix-review (one harness pass)
        │
        └─ Large audit (≥30 fix units OR ≥3 themes)
            → FIX_PLAN.md (overview)
            + FIX_PLAN_PHASE_1.md (e.g. Security findings)
            + FIX_PLAN_PHASE_2.md (e.g. Layer-boundary violations)
            + FIX_PLAN_PHASE_N.md (...)
                │
                ├─ User reviews & edits
                │
                ▼
            For each phase (in dependency order):
                /implement-fix-phase N (creates fix-phase-N-<theme> branch)
                /check
                gh pr create → CI → reviewer → merge
        │
        ▼
/validate-review                 # Independent verification (whole audit, or
        │                          /validate-review N for one phase only)
        ├─ ALL CLEAR? → done
        │
        ▼ (if gaps)
/heal-review → /validate-review → done or manual intervention
```

### Key Discipline: Self-Correcting Harness Pattern

The `/fix-*` commands implement a **Generator/Evaluator harness** inspired by [Anthropic's harness design for long-running AI apps](https://www.anthropic.com/engineering/harness-design-long-running-apps) and [Karpathy's autoresearch](https://github.com/karpathy/autoresearch). The core insight: models exhibit optimism bias when self-evaluating — a separate evaluator is essential.

```
┌─────────────────────────────────────────────────────────┐
│  /fix-check or /fix-review (harness orchestrator)       │
│                                                         │
│  ✗ Cannot write source code directly                   │
│  ✓ Runs evaluator (objective oracle: tooling + grep)   │
│  ✓ Dispatches generators (typed subagents):            │
│      → python-fastapi (for .py files)                  │
│      → react-nextjs (for .tsx files)                   │
│      → flutter (for .dart files)                       │
│  ✓ Re-evaluates after fixes (generator ≠ evaluator)   │
│  ✓ Loops until clean or budget exhausted (max 2-3)     │
│  ✓ Auto-reverts on regression (keep only improvements) │
└─────────────────────────────────────────────────────────┘
```

### Multi-Layer Quality Enforcement

```
Layer 1 — Write-time:    Rules auto-load → guides code generation
                         Security rules prevent injection, hardcoded secrets
Layer 2 — Commit-time:   Tooling blocks mechanical violations
                         SAST (bandit/semgrep) + SCA (pip-audit/npm audit)
Layer 3 — Merge-time:    /check → /fix-check → re-run /check
                         Security scanning + secrets detection (gitleaks)
Layer 4 — Release-time:  Full /review-architecture pipeline
                         Security Confidence Challenge (devil's advocate)
```

This prevents "just fix everything" chaos by:
1. **Forcing planning** before implementation (specs are Sonnet-ready)
2. **Scoping changes** to one phase at a time
3. **Gating merges** with architecture checks
4. **Tracking fixes** in audit logs (REVIEW_FIX_LOG.md)
5. **Delegating implementation** to specialized agents with bounded context
6. **Independent verification** (validator ≠ implementer)

These practices power development on:

## Getting Started

1. Copy relevant `agents/`, `rules/`, and `skills/` to your `.claude/` directory
2. Reference agents in your Claude Code sessions
3. Rules are automatically injected based on file context
4. Invoke skills with `/skill-name` commands
5. **For security**: Copy `THREAT_MODEL.template.md` to your project root as `THREAT_MODEL.md` and fill in assets, trust boundaries, and known risks. Agents read this during implementation to apply appropriate security controls.
